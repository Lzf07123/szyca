# szyca 招新答题系统 · 实现方案（单容器云部署版）

> 版本：v1.1　日期：2026-10-15
> 前置结论：已备案域名 + 国内云服务器，手机走 4G/5G 公网访问；**单容器内含 Nginx、Go、PostgreSQL、Redis，外部反向代理负责 TLS**
> 当前部署形态：预构建镜像从独立应用镜像仓库拉取，低配机器不执行本地编译；所有运行期数据统一落到单卷 `/data`

---

## 1. 目标与范围

### 1.1 核心闭环（MVP 必须覆盖）
```
扫码进入 → 首页(粒子+入场动画) → 填昵称领 token → 拉题答题 → 实时排行榜 → 大屏投影
```
外加两个横向能力：**加入我们（多二维码）展示** 与 **后台管理**（二维码增删改、站点 Logo/页脚等运行期配置、发公告、触发特效、看数据）。

### 1.2 明确不做（一期砍掉）
- NATS JetStream（几百人单机不需要）
- 多副本/多机横向扩容
- 账号注册登录体系（现场用"昵称+一次性 token"即可）
- 历史排行榜回放、积分商城等衍生功能

### 1.3 硬指标（验收门槛，源自原方案 §1.2）
| 指标 | 目标 | 验证方式 |
|---|---|---|
| WebSocket 连接成功率 | > 99% | k6 压测 + 现场演练 |
| 答题提交 P99 延迟 | < 100ms | k6 压测 |
| 排行榜端到端延迟 | < 500ms | 压测 + 人工打点 |
| 答题不丢分 | 断网/重试后分数一致 | 断网演练用例 |

## 2. 总体架构

```
手机(4G/5G) ──HTTPS──> https://quiz.你的域名.com
                              │
                      外部反向代理（TLS 在此终止）
                              │ HTTP + X-Forwarded-For + WS Upgrade
                              ▼
                    szyca 单容器（只暴露 8080）
                    ├─ Nginx :8080（静态资源 + API/WS 反代）
                    ├─ Go    :8081（仅回环）
                    ├─ Redis :6379（仅回环，Pub/Sub + 健康检查）
                    ├─ PostgreSQL :5432（仅回环，权威数据）
                    └─ /data 单卷（数据库、Redis AOF、上传文件）
```

单容器优先保证部署简单和低配可运维。若现场入口流量确实超过轻量服务器公网上行，可再把内嵌前端静态产物发布到 OSS/CDN；API/WS 仍走单容器。

## 3. 技术选型（最终版）

| 层面 | 选型 | 说明 |
|---|---|---|
| 后端 | Go 1.22+ | 标准库为主，依赖少 |
| HTTP 路由 | Go 1.22 `net/http` 增强路由 | 够用，省一个框架 |
| WebSocket | gorilla/websocket | 成熟稳定 |
| 排行榜 | PostgreSQL 全量聚合 + 1s 缓存 | 每人最佳一轮，总分优先、同分用时短 |
| 幂等 | 用户行锁 + attempts 双重唯一约束 | `request_id` 防重试，轮次题目唯一防重复计分 |
| 持久化 | PostgreSQL 16（容器内） | 历史落库 |
| 前端 | React 18 + Vite + TypeScript | 组件化 |
| 状态/请求 | TanStack Query + zustand（可选） | 简化竞态与重试 |
| 视觉特效 | tsParticles（懒加载） | 只首页用 |
| 静态托管 | 镜像内 Nginx | 构建产物复制到 `/app/web` |
| 网关 | Nginx | 容器内反代 + WS 升级；TLS 由外部反代终止 |
| 压测 | k6 | 原生 WS 支持 |
| 部署 | 单容器镜像 + Docker Compose | 远程拉取 `szyca:latest`，不要求本地构建 |

## 5. 数据模型（PostgreSQL）

| 表 | 关键字段 | 说明 |
|---|---|---|
| `users` | id, nickname, token, device_fp, created_at | 一次性 token 不可预测(crypto/rand) |
| `questions` | id, content, options(jsonb), answer, score, sort, active | 现场题库 |
| `attempts` | id, user_id, question_id, selected, correct, score, request_id, round_no, created_at | `request_id` 全局唯一；`(user_id, round_no, question_id)` 唯一，单轮每题只计分一次 |
| `round_questions` | user_id, round_no, position, question_id | 冻结每轮题目顺序，刷新/重启不重新抽题 |
| `qrcodes` | id, title, image_url, active, updated_at | 加入我们二维码；后台增删改，可带标题（展示在二维码下方） |
| `announcements` | id, content, type, created_at | 公告 |
| `quiz_state` | id, state(start/stop), started_at | 全局答题状态 |

排行榜由 PostgreSQL 按最佳轮次聚合，服务端缓存 1 秒；Redis 只负责事件 Pub/Sub 与健康检查。

## 6. 接口与协议

### 6.1 HTTP API（全部走 `/api`）

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/session` | 入参 nickname → 返回 token（一人一码） |
| GET | `/api/quiz/current` | 恢复当前轮题目与题序（带 token） |
| POST | `/api/answer` | 提交当前题答案，带 `request_id` 幂等键；返回下一题服务端截止时间 |
| GET | `/api/rank?top=50` | 排行榜快照（兜底） |
| GET | `/api/config` | 前端运行配置（入口、活动开关） |
| GET | `/api/qrcode` | 启用中的二维码列表（加入我们） |
| POST | `/api/admin/*` | 后台：二维码增删改/站点 Logo 与页脚配置/发公告/触发特效/开始结束答题 |

### 6.2 WebSocket 消息（`/ws?token=xxx`）

| 方向 | 类型 | 说明 |
|---|---|---|
| C→S | `ping` | 心跳（30s） |
| C→S | `subscribe` | 订阅排行/特效频道 |
| S→C | `rank_snapshot` | 连接后立即下发排行快照 |
| S→C | `rank_update` | 增量更新（Top N 变化才推，防刷屏） |
| S→C | `effect` | 特效触发（彩蛋/庆祝） |
| S→C | `announcement` | 公告 |
| S→C | `quiz_state` | 答题开始/结束 |

**推送策略：** 排行榜用"节流"（例如 500ms 聚合一次）+ 只推 Top N 变化项，避免几百人实时全量广播打爆带宽。

## 7. 关键设计决策

### 7.1 不丢分（核心）
- 答题**只走 HTTP POST**，不走 WebSocket。
- 客户端每题生成 `request_id`，提交成功前缓存到 `localStorage`；失败自动重试。
- 服务端 `attempts.request_id` 唯一约束 + 用户行锁双保险，重复提交返回原结果，**不重复计分**。
- WebSocket 只做服务端推送，断线后重连并从 `/api/rank` 拉全量快照补齐。

### 7.2 排行榜排序（总分优先 + 用时排序）
PostgreSQL 每个榜单周期按“每人最佳一轮”聚合：
```
ORDER BY 最佳一轮总分 DESC, 完成用时 ASC
```
服务端缓存 1 秒并节流广播，避免高频重复聚合。Redis 不再保存权威榜，只负责事件广播与健康检查。

### 7.3 防作弊与公平
- 一人一 token，绑定设备指纹（指纹只做弱校验，不阻断）。
- 题目乱序、选项乱序、不可回退、单题限时。
- 同 token 并发提交限流。
- 每轮题目顺序落库，提交时必须命中当前题序；同一轮同一题只允许一条 `attempts`。
- 单题截止时间由服务端记录；`ANSWER_GRACE_SECONDS` 只容忍网络抖动，不改变题时展示。
- 大屏/排行榜昵称**敏感词过滤**（现场投影）。

### 7.4 群活码
- 后台维护多条**群活码/公众号二维码**（标题 + 启停），前端轮询 `/api/qrcode` 展示全部启用项（「加入我们」页响应式横向优先排列、标题在二维码下方）；群满时启用备用二维码，避免 200 人满员失效。

### 7.5 特效触发
- 后台 `POST /api/admin/effect` → Redis Pub/Sub → 所有 WS 连接广播 `effect`。
- tsParticles 只在大屏/首页按需加载，减小主包。

## 8. 部署拓扑与 Nginx 配置

### 8.1 拓扑

```
外部反向代理（公网入口 + TLS 终止）
        │ HTTP，转发到宿主机 8080，带 X-Forwarded-For
        ▼
应用镜像仓库 ──pull──> 轻量应用服务器
                        └── szyca 单容器
                            ├── nginx    :8080 对外
                            ├── app      :8081 仅回环
                            ├── redis    :6379 仅回环
                            ├── postgres :5432 仅回环
                            └── /data          单数据卷
```

### 8.2 本机 nginx.conf 关键片段

```nginx
# 上游
upstream quiz_app {
    server 127.0.0.1:8081;
    keepalive 64;
}

server {
    listen 8080;                 # 由外部反代转发到该端口
    server_name _;

    # 真实 IP 透传（外部反代转发时必须带上）
    set_real_ip_from 0.0.0.0/0;  # 生产环境建议改为外部反代的固定 IP/网段
    real_ip_header    X-Forwarded-For;

    # API
    location /api/ {
        proxy_pass http://quiz_app;
        proxy_set_header Host              $host;
        proxy_set_header X-Real-IP         $remote_addr;
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }

    # WebSocket（两层代理都要开 Upgrade）
    location /ws/ {
        proxy_pass http://quiz_app;
        proxy_http_version 1.1;
        proxy_set_header Upgrade    $http_upgrade;
        proxy_set_header Connection "upgrade";
        proxy_set_header Host       $host;
        proxy_set_header X-Real-IP  $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_read_timeout  300s;   # 长连接超时拉大
        proxy_send_timeout  300s;
    }
}
```

## 9. 外部反代注意事项（必须逐条确认，否则现场会挂）

1. **TLS 在哪终止**：证书在外部反代挂载，本机 Nginx/Go 只走 HTTP，不配证书。
2. **WebSocket Upgrade 穿透两层**：外部反代和本机 Nginx **两层都要**开启 `Upgrade`/`Connection` 头透传，缺一层 WSS 就握手失败。上线前务必用 `wscat` 或浏览器实测 `/ws` 握手。
3. **真实 IP 透传**：外部反代必须转发 `X-Forwarded-For`（或 `X-Real-IP`），本机 `real_ip` 才能拿到访客真实 IP，否则限流/设备指纹全失真。
4. **转发端口约定**：确定外部反代转发到本机的端口（示例用 8080），两侧保持一致；本机 Nginx 对外只暴露这一个端口。
5. **超时对齐**：外部反代若有自己的读超时，也要拉到 300s 以上，否则长连接会被外部反代先掐断。
6. **健康检查**：外部反代使用 `GET /readyz`；它同时检查 PostgreSQL 与 Redis。

## 11. 测试与验收（对照 §1.3）

- **压测**：k6 模拟 500 并发，分别测 `/api/session`、`/api/answer`、`/ws` 连接与推送，出 P99 报告。
- **断网演练**：答题中途断网→恢复→确认分数一致、无重复计分。
- **带宽演练**：现场同规模手机同时扫码，观察 CDN 与服务器带宽水位。
- **WS 穿透演练**：确认经「外部反代 → 本机 Nginx → Go」两层代理后 WSS 握手与长连接稳定。

## 12. 风险与应对

| 风险 | 应对 |
|---|---|
| 外部反代未开 WS Upgrade 或超时太短 | 上线前用 `wscat -c wss://域名/ws?token=test` 实测，两侧超时都拉到 300s |
| 域名备案虽已备，但证书/解析未就绪 | 提前 3 天完成 DNS 解析 + 外部反代证书签发验证 |
| CDN 突发流量超预期 | 前端包体预算 < 300KB，粒子懒加载，图片压缩，提前预热 |
| 现场 4G 信号差 | 备一个现场 WiFi 兜底，二维码指向域名（公网可达）不受影响 |
| 后台被爆破 | admin 接口加简单鉴权 + 限流，管理页不公开入口 |
| 题库出错/答案有争议 | 后台可即时禁用题目，不重启服务 |
