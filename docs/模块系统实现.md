# 模块系统实现

> 更新：2026-11-24
>
> 本文描述契约背后的生成器、注册表、运行时和前端组合实现。开发者接入步骤见 [模块开发契约.md](模块开发契约.md)。

## 1. 源码与构建根

仓库根目录是 Go Module 根：

```text
go.mod
cmd/server/
backend/
modules/
frontend/
```

Docker 构建上下文是仓库根：

- frontend stage 同时复制 `frontend/` 和 `modules/`；
- backend stage 同时复制 `backend/` 和 `modules/`；
- Go 包路径为 `szyca/backend/...` 和 `szyca/modules/<key>/backend`；
- Vite 使用 `@core` 和 `@modules` alias。

## 2. Manifest 加载

生成器入口：

```text
cmd/modulegen/main.go
```

读取：

```text
modules/*/module.json
modules/*/backend/migrations/*.sql
```

处理顺序：

```text
glob module.json
  -> JSON 解码
  -> 目录名与 key 对齐
  -> nil 数组归一化
  -> 校验 schema / 唯一性 / feature / 依赖 / Section
  -> 排序 modules by key
  -> 读取并排序迁移
  -> 渲染生成文件
```

`--write` 直接写入生成文件；`--check` 只比较内容，发现漂移时返回非零状态。

## 3. 校验规则

生成器当前拒绝：

- 非 `schema: 1`；
- 空 label；
- 模块 key 重复；
- key 与目录不一致；
- feature 重复；
- 公开 feature 缺少 path 或 `feature_write_capability`；
- route 不以 `/` 开头；
- route 路径重复；
- route feature 与模块 feature 不一致；
- capability key 重复或缺 label；
- capability 引用未支持固定角色；
- admin tab 重复或缺 permission；
- admin panel 重复、缺少 tab，或引用未注册 tab；
- Section `key@version` 重复；
- Section layout 非法；
- Section feature 未注册；
- requires 指向不存在模块；
- requires 成环；
- 模块缺少 `frontend/index.tsx`；
- 模块迁移同名。

所有模块最终按 key 字典序写入 catalog。运行时构造顺序由 `requires` 决定，不依赖字典序。

## 4. 生成文件

### 4.1 后端 catalog

```text
backend/core/modulecatalog/
  manifests.generated.json
  migrations.generated.json
  catalog.generated.go
```

`catalog.generated.go` 使用 `go:embed` 加载 JSON，提供：

- `All`
- `Get`
- `FeatureKeys`
- `FeatureAllowed`
- `FeatureWriteCapability`
- `Sections`
- `Migrations`
- `CapabilityGrants`

catalog 是纯元数据，不 import 模块实现。

### 4.2 后端实现注册表

```text
backend/core/moduleregistry/registry.generated.go
```

生成器为每个模块 import：

```go
szyca/modules/<key>/backend
```

并生成 `contract.Factory` map。

`Runtime.Build`：

```text
while 未构造模块:
  for manifest in catalog:
    如果 requires 均已在 Services:
      factory(core, resolved module services)
      保存 Module
      保存 Module.Service()
  如果一轮没有进度: 报依赖图不可解析
```

该算法同时验证缺失依赖和循环依赖。

### 4.3 前端 catalog 与 runtime

```text
frontend/src/generated/
  module-catalog.generated.json
  catalog.generated.ts

frontend/src/modules/
  registry.generated.ts

frontend/src/
  module-styles.generated.ts
```

- catalog TS 给导航、Admin tabs、fallback 与测试用；
- runtime registry import 每个模块的 `moduleRuntime`；
- style registry 只 import 已存在的模块 CSS；
- 模块样式位于共享样式之后。

## 5. 后端生命周期

启动顺序：

```text
config.Load
  -> Store.Open
       -> PostgreSQL pool
       -> legacy + generated module migrations
  -> access bootstrap owner
  -> rank/publish
  -> moduleregistry.Build
  -> Runtime.Start
  -> resolve shared runtime interfaces
  -> site service with Gallery/Qrcode providers
  -> HTTP server
```

`Store.Open` 不再隐式播种 Quiz。Quiz 模块构造时调用自己的 `EnsureSeed`。

`Runtime.Ready` 依次调用模块 `Ready`；`/readyz` 只依赖 `contract.Readiness`，不直接依赖 Quiz。

退出时按 catalog 反向顺序调用 `Stop`。

## 6. HTTP 组装

HTTP server 的职责：

- 注册 core routes；
- 接受生成注册表传出的 `[]contract.Module`；
- 对实现 `contract.HTTPModule` 的模块调用 `RegisterHTTP`；
- 提供通用 middleware、文件、媒体和 JSON 能力。

`backend/core/httpapi` 不 import `modules/*`。

每个模块的 route registration 位于：

```text
modules/<key>/backend/routes.go
```

示例模式：

```go
func (m *module) RegisterHTTP(mux *http.ServeMux, api contract.HTTP) error {
	mux.HandleFunc("GET /api/example", api.Feature(
		"example",
		m.handleExample,
	))
	mux.HandleFunc("POST /api/admin/example", api.Permission(
		"example.write",
		func(w http.ResponseWriter, r *http.Request, principal contract.Principal) {
			m.handleAdminExample(w, r, principal)
		},
	))
	return nil
}
```

`api.Permission` 同时执行：

- 管理员会话认证；
- capability 校验；
- 写操作审计。

## 7. 公共响应贡献

### 7.1 `/api/config`

core 先组合共享站点数据：

- footer；
- logo；
- features。

然后遍历 `[]contract.Module`，合并所有 `ConfigContributor.Config()` 返回值。

当前：

- Quiz 贡献 `title / quiz_state / question_seconds`；
- Realtime 贡献 `announcement`。

删除任一模块时，core 不需要改业务分支。

### 7.2 `/api/admin/overview`

core 提供：

- 在线连接数；
- 背景数量；
- uptime；
- goroutines；
- 内存；
- app version。

模块通过 `OverviewContributor` 提供业务指标。当前 Quiz 贡献用户、答题、参与者和题目数量，以及数据库/Redis 状态。

### 7.3 `/api/site`

site 是共享内容组合层：

- feature/nav/footer/section 来自 core + generated catalog；
- gallery 数据通过 `GalleryProvider`；
- qrcode 数据通过 `QrcodeProvider`。

site 不直接查询 `gallery_images` 或 `qrcodes`。

## 8. 跨模块服务

运行时通过 `Runtime.Service(key)` 暴露模块 service。调用方只断言自己需要的窄接口：

```text
lottery -> quiz.EligibilityReader
realtime -> ws.TopProvider
screen -> screen.RankingReader
main -> contract.IdentityValidator
main -> contract.RealtimeRuntime
main -> site.GalleryProvider
main -> site.QrcodeProvider
```

禁止通过 service 强转后调用其他模块未声明的内部方法。

## 9. 前端组合

`moduleRuntime` 包含：

- `manifest`
- `sections`
- `adminPanels`

`registry.ts` 做二次校验：

- key 唯一；
- route path 唯一；
- route feature 与 module feature 一致；
- internal 模块可以没有页面路由。

`App.tsx`：

- 构建 `APP_MODULE_ROUTES`；
- 生成功能开关 gate；
- 生成懒加载 route；
- 判断 fullscreen layout。

`section registry`：

- 先注册 core Section；
- 再展开所有 module runtime 的 sections；
- 相同 `key@version` 重复时启动即报错。

`Admin.tsx`：

- tabs 来自 generated catalog；
- panels 来自 `MODULE_RUNTIMES.flatMap(runtime.adminPanels)`；
- 统一注入 `AdminRuntimeContext`；
- 不直接 import 模块后台组件。

## 10. 迁移合并

legacy migrations 由 core embed；模块 migrations 由生成器读取为 embedded JSON。

迁移器合并后：

1. 检查文件名全局唯一；
2. 按版本名排序；
3. 获取 advisory lock；
4. 校验已应用 checksum；
5. 在单事务中执行 SQL 和写入 `schema_migrations`。

历史迁移文件名、内容和 checksum 不得变化。

## 11. 测试入口

```bash
# 生成器漂移
go run ./cmd/modulegen --check

# 后端
go test ./...
go vet ./...

# 前端
cd frontend && npm run build

# 浏览器
cd tests/browser && node acceptance.mjs
```

Playwright 从 `frontend/src/generated/module-catalog.generated.json` 和 `/api/site`
动态计算当前模块卡片数量，不写死模块数。

## 12. 扩展时的实现顺序

```text
修改 module.json
  -> 后端 service/repository/routes
  -> 前端 runtime/pages/admin/sections/styles
  -> module migrations
  -> module tests
  -> modulegen --write
  -> modulegen --check
  -> build/test/e2e
```

不要先手改注册表；注册表是生成结果，不是实现入口。
